1.1What problem are we solving?

Three downstream APIs (retail-banking, payments, grc) sit behind one Kong gateway. Every request has to pass two gates — and we do not want each API to implement them.

Gate 1 — AuthN (Authentication)

"Who is the caller?"
Verify a signed token, identify the caller.

Gate 2 — AuthZ (Authorization)

"Are they allowed to call THIS endpoint?"
Check the caller's group against the route's allow-list.
Centralise identity at the edge (Kong + Keycloak), so the APIs only do business logic.

1.2OAuth 2.0 vs OpenID Connect (OIDC)

They're related but not the same. OAuth is about permissions; OIDC adds an identity layer on top.

OAuth 2.0

Authorization

"This app may access X on your behalf."

  • Issues an access_token (opaque or JWT)
  • No standard claims about the user
  • Designed for delegated access to APIs
OpenID Connect

Authentication (built on OAuth)

"Here is who the caller is."

  • Issues access_token + id_token (always JWT) + userinfo
  • Standard claims: iss, sub, aud, exp, azp, email…
  • OIDC = OAuth + identity layer
OAuth = "can you do this?"  ·  OIDC = "who are you?"  ·  Keycloak speaks both.

1.3The four OAuth grant flows — pick the right one

A "grant flow" is the recipe for how a client obtains a token. Different callers need different recipes.

Auth Code (+ PKCE)

Web apps / SPAs / mobile

Human in a browser. Redirects to Keycloak login, comes back with a code, exchanged for a token.

Not us

Client Credentials

Service ⇄ Service

No human. Caller knows its client_id + client_secret and POSTs them to the token endpoint.

This is what we use

Password (ROPC)

Legacy

App collects username/password directly. Deprecated — gives the app the user's actual password.

Not us

Device Code

TVs / CLIs

Device shows a code, user authenticates on a phone. For devices without a usable browser.

Not us

Why Client Credentials for FinGate?
The callers in this architecture are other services, not humans clicking a login page.
Each service has its own client_id (admin-client, user-client) and secret.
It exchanges those for a JWT in one HTTP call — no redirects, no browser.
 
POST /auth/realms/fingate/protocol/openid-connect/token
  client_id=admin-client
  client_secret=admin-client-secret-2024
  grant_type=client_credentials

→ { "access_token": "***REDACTED***", "expires_in": 3600 }

1.4What is a JWT, anatomically?

A JWT is just three Base64 strings joined by dots. The third one is a cryptographic signature.

eyJhbGciOiJSUzI1NiIsImtpZCI6IkFCQyJ9
.
eyJpc3MiOiJodHRwOi8v…IiwiYXpwIjoiYWRtaW4tY2xpZW50IiwiZXhwIjoxNzM…
.
MEUCIQDk9b…7T8w_signature_bytes…
Header
algorithm (RS256), key id (kid)
Payload
claims: iss, sub, azp, exp, …
Signature
signed by Keycloak's private key; verified by Kong with the public key

The claim we care about most: azp — the authorized party, which equals the client_id that asked for this token. Kong uses it to figure out which consumer a request belongs to.

// Decoded payload of a token issued to admin-client:
{
  "iss":  "http://finance.kst-devops.com/auth/realms/fingate",   // realm URL — same for every client
  "azp":  "admin-client",                                        // the client that requested this token
  "exp":  1737000000,                                            // unix expiry
  "sub":  "service-account-admin-client",
  "iat":  1736996400
}

1.5Why azp and not iss?

Kong's jwt plugin matches a JWT to a KongConsumer by looking up one claim against the consumer's key field. By default that claim is iss.

If we used iss (default)

admin-client token → iss = realm-url
user-client  token → iss = same realm-url
Kong can't tell them apart — two consumers can't share the same key.
→

With key_claim_name: azp

admin-client token → azp = admin-client → KongConsumer admin
user-client  token → azp = user-client  → KongConsumer user
Same realm key signs both — but Kong identifies the consumer by azp.
Implementation: set key_claim_name: azp on the app-jwt KongPlugin. Both consumers register the same Keycloak realm public key, because Keycloak has only one signing key pair per realm.
